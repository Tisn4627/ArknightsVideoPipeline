# 开发指南

## 架构总览

### 目录布局

项目采用 src 布局，代码位于 `/workspace/src/arknights_video_recognition/`，资源位于 `/workspace/resource/`：

```text
ArknightsVideoRecognition/
├── pyproject.toml                 # 项目元信息与依赖
├── scripts/
│   └── update_resources.py        # 资源同步脚本
├── resource/                      # 内置资源（约 214M，见 资源来源.md）
│   ├── tile/levels.json           # 地图数据
│   ├── avatar/                    # 干员头像库（助战识别）
│   ├── onnx/*.onnx                # 战斗识别 ONNX 模型
│   ├── ocr/maa/{det,rec}/         # Maa finetune OCR 模型
│   ├── data/                      # 战斗/OCR 配置 JSON + 干员职业表
│   ├── template/                  # 模板图片（按钮/小旗/职业图标等）
│   └── config/roi.json            # ROI 任务定义
└── src/arknights_video_recognition/
    ├── __main__.py                # python -m 入口
    ├── cli.py                     # CLI 入口（main）
    ├── pipeline.py                # 主流水线 VideoRecognitionPipeline
    ├── video/                     # 抽帧、切片
    ├── formation/                 # 编队识别
    ├── stage/                     # 关卡名识别
    ├── tile/                      # 地图加载与投影
    ├── battle/                    # 战场分析
    ├── ocr/                       # OCR 引擎封装
    ├── copilot/                   # 作业 JSON 组装
    └── config/                    # 路径与 ROI 配置
```

### 数据流

输入一段战斗录像视频，最终输出 Maa copilot 作业 JSON，整体流程如下：

```text
战斗录像视频
   │
   ▼
VideoFrames（按 resolution 归一化抽帧）
   │
   ├──► 采样开头帧（前 5 秒，每秒一帧）
   │        │
   │        ├──► FormationAnalyzer（编队 OCR + 头像截取）──► List[FormationOper]
   │        └──► StageRecognizer（关卡名 OCR → stageId 查表）──► level dict
   │
   ▼
VideoSlicer（切片为 Clip 序列，逐片段对齐战斗事件）
   │
   ▼
BattleAnalyzer（逐片段：干员检测 → 分类 → 头像匹配 → action 推断）
   │  依赖 OperatorDetector / BattleClassifier / AvatarMatcher / level / formation
   │
   ▼
battle Action 列表
   │
   ▼
pipeline._convert_actions（battle Action → copilot Action，location 坐标转换）
   │
   ▼
CopilotJob（组装 opers + SpeedUp + actions + SkillDaemon + doc）
   │
   ▼
copilot 作业 JSON（写文件）
```

`pipeline.py` 只做串联与转换，不重新实现任何子模块逻辑；各子模块职责单一、可独立测试。

## 各模块职责

### cli.py（命令行入口）

- `main(argv)`：解析参数（`video` / `--ocr` / `-o` / `--stage` / `--resolution`），构造 `VideoRecognitionPipeline` 并调用 `run`。
- 成功返回 0；资源缺失 / 视频无法打开返回 1；关卡未识别返回 2（并打印候选关卡）。
- 成功后在标准输出打印输出文件路径。

### pipeline.py（主流水线）

`VideoRecognitionPipeline` 是核心串联器，对应原 Maa `CombatRecordRecognitionTask`：

- `run(video_path, stage_override, output_path)`：执行完整流程，返回作业 dict。
- `run_to_json(...)`：在 `run` 基础上序列化为 JSON 字符串。
- 内部方法：`_sample_opening_frames`（采样开头帧）、`_recognize_formation`（多帧编队取最优）、`_recognize_stage`（关卡识别，支持手动覆盖）、`_convert_actions`（battle→copilot Action 转换）、`_resolve_output_path`（输出路径命名）。
- 构造时调用 `check_resource()` 校验资源齐全，缺失抛 `ResourceMissingError`。

### video/（抽帧与切片）

- `VideoFrames`：按 `resolution` 归一化打开视频，提供按时间戳取帧（`get_frame_at`）、迭代取帧、`fps` / `duration_sec` 等属性。
- `VideoSlicer`：把视频切片为 `Clip` 序列，对齐战斗事件边界。
- `Clip`：单个片段数据结构，承载该片段的帧与时间信息。

### formation/（编队识别）

- `FormationAnalyzer`：对编队页做 OCR 识别干员名，并截取干员头像，输出 `FormationOper` 列表。
- `FormationOper`：编队干员数据结构（含干员名、头像图像等）。

### stage/（关卡名识别）

- `StageRecognizer`：对 `BattleStageName` ROI 做 OCR，查 `levels.json` 得到关卡 dict（含 `stageId` / `code` / `name` / `tiles` / `view`）。
- 查表采用 4 级降级匹配：
  1. 原文精确查表（stageId / code / levelId / name 任一命中）；
  2. 应用 `BattleStageName` 的 `ocrReplace` 正则规则归一化后查表；
  3. 归一化查表（去空白、小写；code 类文本把易混字母 `i/l/o/s/z` 还原为数字 `1/1/0/5/2`）；
  4. `difflib` 模糊匹配（相似度 >= 0.6 视为候选）。
- `recognize_by_manual(stage_key)`：用户手动指定（code / name / stageId）直接查表，跳过 OCR。

### tile/（地图加载与投影）

- `loader.py`：加载 `levels.json`，提供 `load_levels` / `find_level` 按多种键查表。
- `calc.py`：3D 透视投影矩阵计算，精确移植自 `Arknights-Tile-Pos/python/main.py` 的 `Calc` 类，把地图格子世界坐标投影到屏幕像素坐标。对外提供模块级便捷函数 `get_tile_screen_pos` / `get_all_tile_positions` / `get_character_screen_pos` / `get_withdraw_screen_pos` / `get_skill_screen_pos`。

### battle/（战场分析）

- `OperatorDetector`：YOLOv8 干员检测，输出 `Detection`。
- `BattleClassifier`：技能就绪 3 分类、部署方向 4 分类（加载 `skill_ready_cls.onnx` / `deploy_direction_cls.onnx`）。
- `AvatarMatcher`：场上头像 ↔ 编队头像匹配；含 `screen_pos_to_tile`（屏幕坐标 → 格子 `[row, col]`）。
- `BattleAnalyzer`：推断 action 列表（双指针主循环，对齐 Maa `analyze_battle`），输出 `Action`（`Deploy` / `Skill` / `Retreat`，含 `location` / `direction` / `ts` 视频时间戳）。本项目以视频时间点作为 actions 的时间点，不推断 kills / cost 条件。
- `DeploymentAnalyzer`：部署栏分析（对齐 Maa `analyze_deployment`），含 `BattleButtonDetector`（pause/speed 按钮检测）。

### ocr/（OCR 引擎封装）

- `OcrEngine`：封装 `rapidocr-onnxruntime`，支持双模型源切换，提供 `recognize(image, roi)` / `recognize_text(image, roi)`。
- `OcrSource`：模型来源枚举（`MAA_MODEL` / `DEFAULT`）。
- 内部按 source 缓存 RapidOCR 实例（构造较慢，确保每个 source 只加载一次）；OCR 文本会按 `ocr_config.json` 的等价类规则做归一化替换。

### copilot/（作业 JSON 组装）

- `CopilotJob`：作业组装器，按 Maa copilot schema 组装，提供 `add_oper` / `add_action` / `add_speedup` / `add_skill_daemon` / `set_doc` / `save` / `validate` 等。
- `Action` / `Oper` / `CopilotDoc` / `OperRequirements`：对应 schema 各部分的数据类。
- `ActionType` / `Direction`：枚举常量类（英文值），并附中文→英文映射。
- `location_from_tile(row, col)`：把 tile 的 `[row, col]` 转成 copilot 的 `location` `[x=col, y=row]`。

### config/（路径与 ROI 配置）

- `settings.py`：项目根 / 资源路径常量、默认参数（`DEFAULT_RESOLUTION` / `DEFAULT_OCR_SOURCE` / `MINIMUM_REQUIRED`）、`ResourceMissingError` 与 `check_resource()`。资源目录可用环境变量 `AVR_RESOURCE_DIR` 覆盖。
- `roi.py`：ROI 配置，从 `resource/config/roi.json`（由 Maa `tasks.json` 提取的 22 个视频识别任务）加载，提供 `load_roi` / `get_roi`。

## 关键设计点

### 地图识别为何用标准 Arknights-Tile-Pos

地图识别采用社区标准的 Arknights-Tile-Pos 形式：单文件 `levels.json`（940 关卡，含每个关卡的 `tiles[row][col]` 与 `view` 视点）+ 3D 透视投影矩阵计算（`tile/calc.py`）。

选择矩阵计算而非图像识别的原因：

- **准确率 100%**：`levels.json` 直接给出每个格子的世界坐标，`calc.py` 用固定的透视投影矩阵（FOV=20°、绕 X 轴 30°、绕 Y 轴 10°）把世界坐标投影到屏幕像素，结果确定且精确，不依赖图像内容。
- **与上游一致**：`calc.py` 精确移植自 `Arknights-Tile-Pos/python/main.py`，数值结果与原版偏差 0px，可直接复用社区已验证的地图数据。
- **零训练成本**：新关卡只需更新 `levels.json`，无需训练或调参。

### OCR 双模型源切换机制

`OcrEngine` 通过 `OcrSource` 枚举在两套模型源间切换：

- `maamodel`（默认）：复用 Maa 的方舟 finetune PaddleOCR onnx 模型（`resource/ocr/maa/det/` 检测 + `resource/ocr/maa/rec/` 识别）。保留方舟专用精度。
- `default`：使用 RapidOCR pip 包自带的默认模型，无需额外模型文件。

实现要点（见 `ocr/engine.py`）：

- RapidOCR 实例按 source 缓存（`_ENGINE_CACHE`），每个 source 只加载一次。
- `maamodel` 构造分两步：先用 maa 的 det 模型构造（rec 暂用默认模型，因为 maa 的 rec onnx 未内嵌字符表，直接构造会断言失败），再用显式配置（含 `keys_path`）把识别器替换为 maa 的 rec 模型 + `keys.txt`。
- OCR 识别结果按 `ocr_config.json` 的等价类规则做字符归一化（如繁简 / 易混字统一），提升后续查表命中率。

### location 坐标转换

存在两套坐标约定，转换通过 `copilot.location_from_tile` 完成：

- tile 模块与 `levels.json`：`tiles[row][col]`，即 `[row, col]`（行、列）。
- Maa copilot schema：`location` 为 `[x, y]`，其中 **x = 列 (col)、y = 行 (row)**。

`location_from_tile(row, col)` 返回 `[col, row]`，即 `[x, y]`。在 `pipeline._convert_actions` 中，battle 的 `[row, col]` 经此函数转成 copilot 的 `[x, y]`。坐标可在 [https://map.ark-nights.com/areas](https://map.ark-nights.com/areas)（"坐标展示"设为"MAA"）核验。

### battle Action → copilot Action 的转换

`pipeline._convert_actions` 把 `battle/analyzer.Action` 转成 `copilot.Action`：

- **type**：`Deploy` / `Skill` / `Retreat` 字符串经 `_BATTLE_TYPE_TO_COPILOT` 映射到 `ActionType` 常量（值同为字符串，显式映射便于排查）。
- **location**：battle 端已输出 `[col, row]`（对齐 Maa `[loc.x, loc.y]`），直接透传为 copilot 的 `[x=col, y=row]`。
- **direction**：`Right` / `Down` / `Left` / `Up` / `None` → `Direction` 常量；仅 `Deploy` 输出 direction（`Skill` / `Retreat` 不需要朝向，省略保持 JSON 简洁）。
- **video_time**：battle 端的 `ts`（视频时间戳）透传为 `video_time`，仅在使用 `--with-video-time` 时输出到 JSON。

### 资源说明

`resource/` 总大小约 214M，所有子目录均纳入版本控制（开箱即用），详细清单见 [资源来源.md](./资源来源.md)：

- `avatar/`（约 81M）：干员头像库，用于助战识别。
- `tile/levels.json`（约 67M）：940+ 个关卡的标准地图数据。
- `onnx/`（约 40M）：3 个战斗识别 ONNX 模型。
- `ocr/maa/`（约 13M）：Maa finetune PaddleOCR 模型。
- `data/`（约 15M）：战斗/OCR 配置 + 干员职业表。
- `template/`、`config/`：模板图片与 ROI 配置。

其中 `avatar` / `tile` / `config` / `data` 由 GitHub Actions workflow 定期自动同步；`onnx` / `ocr` / `template` 已在仓库中但不通过 workflow 自动同步，由开发者本地手动更新。详见 [GitHub Workflow 说明](./workflow说明.md)。

精简清单与同步逻辑见 `scripts/update_resources.py` 的 `build_sync_plan`。

## 扩展点

### 如何加新关卡类型

新关卡无需改代码：只要上游 `ArknightsGameResource` 的 `levels.json` 收录该关卡，`python scripts/update_levels.py` 同步 `resource/tile/levels.json` 即可。`tile/loader.find_level` 支持按 stageId / code / levelId / name 多键查表，`stage/recognizer` 的 4 级降级匹配会自动适配新关卡名。

### 如何换 OCR 模型

- 切换现有模型源：CLI 用 `--ocr default` / `--ocr maamodel`，或在代码中构造 `OcrEngine(source=OcrSource.DEFAULT)`。
- 替换模型文件本身：把新的 onnx 模型放到 `resource/ocr/maa/{det,rec}/`（注意 rec 需配套 `keys.txt`），或修改 `ocr/engine.py` 的 `_build_maa_engine` / `_build_default_engine` 指向新路径。

### 如何调整 ROI

ROI 配置在 `resource/config/roi.json`（22 个任务定义，从 Maa `tasks.json` 提取）。修改方式：

- 直接编辑 `roi.json` 中对应任务的 `roi` / `rectMove` 等字段。
- 从 Maa 重新提取：`python scripts/update_resources.py --regen-roi`（会从 `/Maa/resource/tasks/tasks.json` 重新提取 22 个视频识别任务，覆盖 `roi.json`）。
- 代码侧通过 `config/roi.get_roi(task_name)` 读取，`BattleStageName` 在 `roi.json` 缺失时有兜底默认值 `_DEFAULT_STAGE_ROI`。

### 如何改进切片策略

切片逻辑在 `video/slicer.py`（`VideoSlicer.slice()`）。可调整切片对齐战斗事件的边界判断规则。改完后用端到端冒烟测试（见下文）验证 `actions` 序列是否合理。

## 测试方式

### tile 一致性验证

`tile/calc.py` 精确移植自 `Arknights-Tile-Pos/python/main.py`。可对同一关卡用本项目与原版 `main.py` 各算一遍屏幕坐标，比较结果应偏差 0px，用以确认移植正确性。

### OCR 加载验证

构造 `OcrEngine` 并对样例图像调用 `recognize` / `recognize_text`，验证 `maamodel` 与 `default` 两个 source 都能正常加载并返回文本：

```python
from arknights_video_recognition.ocr.engine import OcrEngine
import cv2

img = cv2.imread("sample.png")
eng = OcrEngine(source="maamodel")
print(eng.recognize_text(img))
```

### copilot schema 验证

`CopilotJob.validate()` 会校验作业合法性（`stage_name` 非空、`actions` 非空、`Deploy` 含 `name`/`location`/`direction`、`location` 为长度 2 的 `[int, int]`、`MoveCamera` 含 `distance`）。生成的 JSON 可对照 `/Maa/docs/zh-cn/protocol/copilot-schema.md` 做字段核验。

### 端到端冒烟

用一段标准战斗录像跑通整条流水线，确认能产出合法作业 JSON：

```bash
python -m arknights_video_recognition /path/to/battle.mp4 -o /tmp/job.json
```

检查：输出文件存在、`stage_name` 正确、`actions` 以 `SpeedUp` 开头以 `SkillDaemon` 结尾、`Deploy` 动作含合法 `location` 与 `direction`。也可用 `--stage` 强制指定关卡以排除 OCR 干扰。

## 贡献约定

- 代码注释用中文（与现有代码风格一致）。
- 不修改上游仓库（`/Maa`、`/ArknightsResources`）；本项目通过 `scripts/update_resources.py` 只读取并复制所需文件到 `resource/`。
- 遵循 src 布局：源码放 `src/arknights_video_recognition/`，资源放 `resource/`，脚本放 `scripts/`。
- 新增依赖需同步更新 `pyproject.toml` 的 `dependencies`。
- `roi.json` 是项目自有产物，常规资源同步不会覆盖它；改动 ROI 后若运行 `update_resources.py` 需注意不要带 `--regen-roi`（除非确实想从 tasks.json 重新提取）。
